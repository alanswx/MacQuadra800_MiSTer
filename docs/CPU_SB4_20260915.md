# Four-entry store queue (2026-09-15, candidate)

Built on checkpoint 14 (stack4); parent-repository module
`rtl/wombat_store_buffer.sv` only, with its bench
`verilator/tb_wombat_store_buffer.sv`.  Tree `/tmp/stack5-cand.*`.

## Why

The checkpoint 14 Speedometer profile (975 M cycles) has 13.6 M cycles of
bus reads waiting behind queued stores and 15.0 M cycles of stores
waiting for a queue slot (`read_behind_store_cycles`,
`sb_full_stall_cycles`); every read to memory waited until the two-entry
queue was empty, whatever the addresses.

## What changes

- Depth 4 (the entries are small arrays; a pop shifts, a push writes the
  first free slot after the shift).
- A read passes the queued stores when it cannot alias them: it
  addresses RAM or the ROM window and no queued store shares its 16-byte
  line (a cache fill reads whole lines).  It still waits for a store
  already on the bus, and the drain resumes behind it.  Device reads and
  non-qualified writes keep the full drain order.  A read that keeps
  arriving cannot starve the queue: the fifth store stalls the core, which
  then issues no reads, and the drain runs.

The bench keeps the same-line read ordered (T2), adds the passing read
of another line ahead of a second queued store (T2b), the device read
that does not pass (T2c), and five stores through the four slots in
order (T3); all pass.

## Version 2: the bypass starved the drain

The first version let any non-aliasing read pass whatever the queue
held.  The boot A/B ran at half speed (41.3 M dispatches against
75.8 M; aligned stores waited 19.6 clocks each in the cache's pass
state): instruction fetches are exactly such reads and the fetch engine
issues one nearly every idle cycle, so the drain never started until the
queue was full and the core had stalled behind a fifth store.  Version 3
lets reads pass only while the queue holds at most two stores; from
three up the drain has the bus.  The module bench (a passing read ahead
of a second queued store, a same-line read that waits, a device read
that waits, five stores through four slots) and a posted-store bench
pass; the boot A/B and fits rerun.  The version 2 fit at seed 20 needed
39,603 ALMs (+190 for the two extra entries) and failed routing.

Version 3 booted at exactly the same half speed, so the occupancy limit
was not the mechanism.  It is the fill: a cache fill holds the bus for
four beats, the drain cannot start under it, the queue reaches its limit
during the fill and the next store waits for the whole drain.  With
strict ordering the fill instead waits for the one queued store.  The
bypass is withdrawn; version 4 is the four-entry depth with the original
order (reads and non-qualified writes wait for an empty queue).  Its
gain is bounded by the queue-full stalls alone (15.0 M cycles, 1.5 %).

## Results so far

Latency fixture 2,022 (checkpoint 14: 2,037); Sieve identical.  Corpus,
boot A/B, simulated Speedometer and fits at seeds 22 and 20 running.
The expected gain is bounded by the 28.6 M cycles above, about 2 % if
most of them go.

### Version 4 (depth 4, strict order): boot level, fits fail

Boot A/B 75,856,494 dispatches (checkpoint 14: 75,840,887): queue-full
stalls 5.3 M -> 0.7 M cycles, reads behind stores 6.4 M -> 7.3 M (they
now wait for a deeper queue), net nothing.  Fits at seeds 22 and 20 both
failed routing (39,611 and 39,448 ALMs).  Parked unless the simulated
Speedometer shows more than the bracket's 1.5 % bound; the change is not
in the repository (the working-tree module and bench were restored).

Simulated Speedometer: **983,044,263 cycles against checkpoint 14's
972,509,351 (+1.1 %)**: queue-full stalls 14.9 M -> 2.8 M, reads behind
stores 13.2 M -> 18.1 M, reads with stores pending 50.9 M -> 54.3 M.  A
deeper queue only makes the reads that must wait for it wait longer.
**Rejected 2026-09-15.**  The store side's remaining cost is the ordered
wait itself; the fix would be a read that passes non-aliasing stores
without holding the bus for a whole fill (a fill that yields the bus to
one drain between beats), which is a cache change, not a queue change.
