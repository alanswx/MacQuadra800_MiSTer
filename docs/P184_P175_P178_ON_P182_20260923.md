# P184: P175-P178 back on top of P182, with the stale next-row fix and the data banks kept for hinted fetches

P175b (the instruction hint bus and mirror RAMs), P177 (the return-address stack) and P175c/P178
(half-depth mirrors, the one-clock hit across two lines) left HEAD on 2026-09-22 because P178 hung Mac
OS 8.1 during extension loading on hardware and in some full-machine sim runs (ATM's F-line system
error, `RESUME-cpu-speed-20260922b.md`).  P184 is a three-way merge of `8ce901c` onto P182 (base P174
`0dfd1a8`) with two fixes.

## Fix 1: the cross-line hit's next-row read had no write check (the P178 hang)

`fast_xline_idle` (P178) acknowledges a longword spanning lines R and R+1 in one clock: word 3 of R from
the idle read, word 0 of R+1 from the pair banks read at `x_rowp1`.  Its validity was `idle_data_valid`,
which rejects a write landing on `x_row` in the read clock but not on `x_rowp1`.  A posted store's
C_PASS write (`store_hit_write` on `m_ack`) lands exactly in the clocks where `posted_hint_read` keeps the
idle read up, so a store to line R+1 followed by a longword read at offset 14/15 of line R returned the
pre-store word 0 -- Pascal's 2-mod-4 stack longwords make that pattern common, and whether the store's
acknowledge coincided depended on SDRAM timing (hence "a race").

`idle_next_valid` is `idle_data_valid` with the write check extended to `x_rowp1`; `fast_xline_idle`
uses it.  Evidence (full-machine sim, `scratch/sim_p178_boot/`): a probe for "P178 would have
acknowledged stale next-row data" fired 200+ times during the 8.1 boot; the fixed build replaying the
exact options of two runs that crashed (81b to frame 6000, 81d to 4200) boots to the Finder with no
exception, where the unfixed build hit the F-line error at frame ~4050.  (The fix changes execution
after the first stale read, so a replay is not exact.)

## Fix 2: P175b let every one-clock fetch take the data banks' idle read

The new Int. Matrix and Sieve fixtures showed P175b costing +12 % and +5.7 % (P177/P178 neutral).
P175b points the architectural banks at the instruction hint whenever a fetch is presented
(`c_ihold = mem_req && sel_instr`), including the clock a one-clock fetch (fast_ihit, served from the
instruction mirrors) acknowledges in -- so the data side's idle read was lost to every fetch, and the
load after it took the registered path (Matrix reads 1.03 -> 1.47 clocks mean).  P174's single hint
bus had moved on to the data side in the fetch's acknowledge clock.

`wombat_cpu` (and the compat wrapper) register the instruction hint's row and word (`ihint_q`); a fetch
in its first presented clock (`!pres_v`) that matches it is `ifetch_hinted_first`, and `c_ihold` is
withheld for it: the banks stay on the data hint.  If such a fetch does not hit, the cache holds its
C_IDLE acceptance for that clock (`c_instr && !c_ihold`), and from the next clock (`pres_v`) the banks
follow it as before.  The instruction idle hit needs no guard: it checks the index its read was made at.
