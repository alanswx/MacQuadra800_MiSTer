# One-entry translation bypass in the MMU (2026-09-13, candidate)

Follows the adopted registered cache-hit admission
(`CPU_CACHE_EARLY_REVIEW_20260913.md`). Candidate only until the hardware
section below is filled in.

## Why this is next

After the cache change, a translated warm hit costs 3 clocks: 2 from the
core's request to qualified cache admission (one of them the MMU's ATC
lookup pipe, `l_ld` -> `row_q` -> `lk_fresh`) plus 1 to consume, while a
TC-off hit costs 3 as well but with only 1 to admission. The one-clock ATC
pipe is therefore the whole difference between running with translation on
(Mac OS) and off. The boot profile shows the machine spends 14.7 % of cycles
in `S_FETCH` and 5.1 % in `S_IMMF`; the sequential instruction lookahead in
the cache (`ipred`) answers at the admission edge with no RAM read, so for
it the ATC pipe clock is the only thing left to remove.

## What the change is

`ap040_mmu.v` keeps a registered copy of the most recent piped ATC hit:
`{u_valid, u_row[4:0], u_tag[16:0], u_ent[44:0]}` plus a 32-bit shadow of
`tc`. A request whose `{a_row, a_tag}` equals the copy hits combinationally
(`u_hit`) in its own request cycle: `atc_hit`, `h_ent`, `need_walk` and
`pass_ok` all accept `u_hit` alongside `lk_fresh`. Everything downstream
(permission and supervisor faults, the M-bit walk on a write to a clean
page, cache mode, physical address) is computed from the copied entry
through the unchanged decisions.

The copy is dropped on every event that can change the ATC: a walker fill
(`fill_we`), a PFLUSH clear or sweep (`pf_req`, `sweep_on`, which also
covers the PTEST pre-flush), any change of `tc`, and reset. The walker picks
its fill way through its own port-B compare, so the bypass cannot disturb
replacement. Cost: 68 flops plus a 22-bit equality compare and a 45-bit
2:1 mux ahead of `pa_out`.

Patch: `/tmp/utlb-cand.Ip36yu/utlb.patch` (63 lines), candidate
`ap040_mmu.v` SHA256 `31c8f77a4098d384ef025f1210c0777f0de96632448315b30294375828bbabfb`,
baseline `9e9a1580...`; core `0c3a81bd...` and cache `77882b83...` unchanged.

## Results so far

- AP68040 suite in the isolated tree: 11 of 11 pass (including `mmu`, which
  covers remaps, write-protect and supervisor faults, M-bit walks, PTEST
  installs and PFLUSH staleness).
- Handoff latency fixture (`/tmp/utlb-lat.Z84qsP`): **2,127 -> 1,992 clocks**
  (-6.3 %; -9.0 % against the pre-cache 2,188). Translated instruction
  fetches move from 3 to 2 clocks (phases 3 to 8: 16 of 23 fetches at 2,
  the rest are first-touch misses or line starts). Translated warm data hits
  stay at 3, as expected: the core presents the address and the request in
  the same cycle, so the cache has no early cycle to read its RAM in.
  Idle-admission completions fall from 61 to 32 because those fetches now
  complete through the lookahead instead.

Pending: full-machine boot A/B against the adopted RTL, corpus gate, Sieve
sweep (TC off, identical expected), matched trimmed seed-24 fit, hardware.

## What it does not do, and what would

Data hits need the cache to see the index one clock before the request.
That is a core change (present the effective address a cycle ahead of
`mem_req` when no transfer is in flight), not an MMU or cache change, and it
is the natural next step if the Speedometer-interval profile shows data
hits as a large share of `S_MRD` time.

The wait states shed cycles while their entry counts rise, and the
throughput lands as more decode/execute entries. `C_LOOK` grows because a
request that now arrives in its own cycle no longer has the idle read
settled (the data-hit case discussed above); it is still a net win because
the MMU clock it replaces was spent on every access. Same frame, byte-
identical screenshot, same highest LBA, no faults. Corpus gate: 34,740,491
cycles, identical to baseline, 0 REAL diffs. Sieve sweep: byte-identical at
all 16 offsets (TC off). Coverage note: PFLUSH/TC-change stress on the copy
is exercised by the AP `mmu` suite (PFLUSHA, PTEST staleness, remaps) and
incidentally by the boot; no dedicated bench exists yet.

Deployed through the guard as
`/media/fat/_Unstable/MacQuadra800_utlb_trim_seed24_20260913.rbf` (all

third run of a set on two different trimmed builds and not at all on the
cache-early set. Not averaged away; a second set of three follows.

Same RBF, same guard flow (all exits 0). Runs **0.503 / 0.504 / 0.503**,
fresh alert each, guest clock 2:40 / 2:44 / 2:47 AM, no anomaly. Evidence
`scratch/perf_utlb_seed24_20260913_set2/RESULTS.txt` with timestamps

+154 s each). Across both sets the five valid runs are all 0.503 or 0.504;
mean **0.503333**, **+3.71 %** over the cache-early checkpoint 0.485333 and
+9.7 % over the previous accepted 0.458667.

**Accepted 2026-09-13** (single-entry version, MMU SHA256 `31c8f77a...`).
A per-space (instruction/data) variant of the copy is already in the next
candidate together with the core's address hints; see
`CPU_ADDR_HINT_20260913.md`.

The negative-time anomaly on set 1 run 3 (uptime 631 to 789 s after core
load) sits in the same uptime window as the valid cache-early run 3 (646 to
799 s), so it is not a fixed-uptime wrap; it behaves like an intermittent
race in the guest timer path and remains a separate diagnosis
(`SPEEDOMETER_TIMING_DIAGNOSTIC.md`, observer fixture).
