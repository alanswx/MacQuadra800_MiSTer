# Line-crossing data reads served from the cache (2026-09-15, candidate)

Built on stack3 (checkpoint 12 plus the RTS/LINK/UNLK folds of
`CPU_CTRL_FLOW_20260914.md` v6); cache only, script
`scratchpad/xline.py`, tree `/tmp/stack4-cand.*`.

## Why

The calibrated Speedometer profile on the 16 KB caches (simulated CPU
Mix 0.780 against 0.779 on hardware) still spends 50.5 M of its 991 M
cycles on reads passed around the data cache, and 39.6 M of those are
3.76 M reads that straddle two 16-byte lines: a longword at offset 13,
14 or 15, or a word at 15.  Each takes 10.5 clocks through the bus
adapter's split (two SDRAM accesses).  Mac code aligns to two bytes, so
a quarter of all misaligned longwords cross a line; the checkpoint 5
write path already serves the other three quarters (`span2`) from the
cache.

## What changes

`xline` classifies the crossing read and it no longer bypasses.  In
`C_LOOK` the first lookup is the ordinary one for the line holding word
3; on a hit its word is kept in `fill_hold` and, in the same cycle, the
tag row and word 0 of the next row are read (`xlook_read` redirects
`tag_ridx` and the data indexes to `{0, set+1}`; the tag is `tag+1` when
the set wraps).  The following cycle (`xlook`) compares against the next
line's tag (`compare_tag`), takes its word 0 (`q_word` forced to 0) and
assembles the pair with `span_extract`, acknowledging in the third cycle
after acceptance.  Either lookup missing, a port-B write in the first
cycle, or a snoop on the next line's row in either cycle, falls back to
the bypass (`C_PASS`, which forwards the still-held request exactly as
an accepted bypass would).

Version 1 bypassed on a second-line miss as well.  The boot A/B showed
that this is the common case there (bypassed crossing reads fell only
from 607 K to 554 K, and the two wasted lookups cost 97 K dispatches).
In a sequential walk the second line is the next one needed, so version
2 fills it on a clean miss: the fill starts at word 0 (`r_row`, `r_tag`,
`r_addr` and the victim way move to the next line; the first line's word
3 waits in `fill_hold2`) and the crossing pair is acknowledged on the
first beat, then the rest of the line lands as any fill's does.  A
first-line miss still bypasses.

Page-crossing accesses never reach the cache (the core splits them
byte-wise on the logical address), so both halves of a crossing read
translated identically and cannot fault differently.  Stores are
untouched: a crossing store still bypasses and invalidates both sets.

Cost: two SETW+TAGW-bit registers, three flags, a 2:1 on the tag read
index and on the data indexes, one more term in the compare-tag select.

## Results so far

Version 1: AP 11/11, corpus 33,738,108 (identical to stack3: the corpus
runs with the caches off), latency 2,037; boot A/B 75,603,896 dispatches
(stack3 75,700,859), the second-line misses above.  Version 2: AP 11/11
and corpus identical (the corpus runs with the caches off, so neither
checks this path's data); a directed test 15 in `tb_ap040_cache_snoop.v`
now does: cold first line bypasses, first-hit/second-miss fills the
second line and returns the right pair, both-hit longs at offsets 13 and
15 and the word at 15 come back with no memory read in at most five
clocks, a store into the second line is seen by the next crossing read,
and the set-wrap pair (last set to first set, next tag) hits.  Boot A/B:
**75,840,887 dispatches** (+0.19 % over stack3's 75,700,859; the best
boot bracket so far), no faults, same frame; bypassed crossing reads
607 K -> 231 K (6.4 M -> 2.5 M cycles), passed-read cycles 50.1 M ->
46.1 M, data fills 1.52 M -> 1.60 M (the second-line fills).  Simulated
Speedometer and fits at seeds 20 and 22 running.  Expected: about 6 clocks saved per
crossing read on double hits, up to 2.3 % of the bracket.
